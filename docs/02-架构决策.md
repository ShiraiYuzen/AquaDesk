# 02 · 架构决策记录（ADR）

每一条都记「选了什么 / 为什么不选别的 / 什么时候该反悔」。

---

## ADR-001 · 用 C# .NET 8 + WPF，不用 Electron / Tauri

**决定**：WPF。

**理由**
- 常驻进程，空闲内存要压到 60MB 以内。WPF 空窗口约 25–35MB，Electron 起步 150MB+。
- Dock 要干的事全在 Win32 层：改扩展窗口样式、枚举窗口、调 DWM、装全局钩子。C# 的 P/Invoke 是最短路径。
- 单文件发布 ~30MB（框架依赖）或 ~70MB（自包含），用户能接受。

**反悔条件**：如果要做的界面复杂度爆炸（比如自绘整套控件库、大量动效编排），WPF 的 XAML 会写得很痛苦，那时候再考虑 Web 技术栈。

## ADR-002 · Dock 窗口用 `WS_EX_NOACTIVATE`，不做「激活后再还原焦点」的 hack

**决定**：窗口创建时就打上 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`。

**理由**
- 不加 NOACTIVATE，点 Dock 图标时 Windows 会先把焦点给 Dock 窗口，导致当前应用失焦、任务栏闪烁。
- 常见的补救办法是「先记录前台窗口句柄，点完再 `SetForegroundWindow` 还原」——但 Windows 有前台锁定策略，
  还原经常失败，而且会闪一下。不如一开始就不抢。
- NOACTIVATE 窗口照样收鼠标消息，点击不受影响。

**代价**：Dock 不能接收键盘输入。将来做「聚焦搜索」输入框时，那个窗口必须单独开一个可激活的窗口，不能挂在 Dock 上。

## ADR-003 · 图标从开始菜单 `.lnk` 拿，不扫 Program Files

**决定**：枚举 `%ProgramData%\Microsoft\Windows\Start Menu\Programs` 和用户级同名目录，取 `.lnk`。

**理由**
- 开始菜单就是「用户认为已安装且值得启动的应用」的权威列表，Program Files 里混着卸载器、运行时、驱动组件。
- `.lnk` 的图标由 Shell 解析，`SHGetFileInfo` 一把梭，不用自己读 PE 资源段、也不用处理 `.ico`/`.png`/资源索引。
- 用户装了新软件，重扫一次就能出来，不需要维护白名单。

**代价**：绿色软件（没建快捷方式）扫不到。后续在 M5 加「手动拖入 .exe / .lnk 到 Dock」补上。

## ADR-004 · 放大镜用 `RenderTransform`，不改宽高

**决定**：每个图标挂 `ScaleTransform`，锚点 `(0.5, 1)`，鼠标移动时算高斯衰减写入 `Scale`。

**理由**
- 改 `Width/Height` 会触发 measure + arrange，整个 Dock 每帧重排，鼠标一动 CPU 就上去。
- `RenderTransform` 走合成层，不参与布局，60fps 基本零成本。
- 锚点放底边中点，放大时图标向上长，底部基线不动——和 macOS 观感一致。

**已知缺陷**：目前图标放大时会互相重叠。macOS 是让邻居往外让位的，要做到那个效果，
需要按每个图标的 `Scale` 反算累计位移，再给每个 item 加 `TranslateTransform`。放在 M1 收尾做。

## ADR-005 · 窗口用 `AllowsTransparency=True`，暂时放弃真毛玻璃

**决定**：M1 用半透明渐变 + 圆角 Border 模拟玻璃，不开 DWM Acrylic。

**理由**
- `AllowsTransparency=True` 的窗口走软件渲染，DWM 的 backdrop 对它无效——两者不能同时要。
- 真毛玻璃（`SetWindowCompositionAttribute` / Win11 的 `DWMWA_SYSTEMBACKDROP_TYPE`）要求窗口不透明，
  圆角得另外用 `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` 或 Region 裁。
- M1 先把交互跑通，视觉精度留到 M3。

**M3 的路线**：关掉 `AllowsTransparency` → 开 Acrylic/Mica → Win11 用系统圆角 API，Win10 用 `SetWindowRgn` 兜底。

## ADR-006 · 不用管理员权限，不碰 explorer.exe

**决定**：`requestedExecutionLevel = asInvoker`，永不注入、不替换系统进程。

**理由**
- 要求管理员权限 = UAC 弹窗 = 用户第一印象就崩，而且杀软会盯得更紧。
- 替换/注入 explorer 的方案一旦崩了，用户整个桌面（含任务栏、托盘、桌面图标）全没，属于不可接受的风险。
- 只改自己窗口的样式、只读开始菜单，普通权限完全够用。

**代价**：隐藏原生任务栏需要额外手段（改 `SHAppBarMessage` 或让用户手动设自动隐藏），不能强来。

## ADR-007 · 液态玻璃用「四层渐变」模拟，不追 DWM 真折射

**决定**：tint（可调透明度）+ sheen（镜面高光）+ rim（亮边）+ 底部内阴影，四层叠出来。

**理由**
- macOS 26 的 liquid glass 核心是「高透明 + 强高光 + 边缘折射」，不是重磨砂。所以不需要真 blur 也能接近。
- 真 backdrop（DWM Acrylic / `DWMWA_SYSTEMBACKDROP_TYPE`）要求窗口不透明，而我们的圆角靠
  `AllowsTransparency=True` 实现——两者互斥，硬上会丢掉平滑圆角。
- 另一条路是 BitBlt 抓屏自己模糊，但 Dock 是 Topmost，会把自己抓进去形成反馈；
  `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 能解决，可副作用是截图工具也看不到 Dock，得不偿失。

**踩坑记录**：高光层第一版给了 65% 白，结果整条 Dock 变成磨砂塑料，壁纸完全看不见。
现在 sheen 顶部最多 24% 白，透明度默认 0.26，才是玻璃该有的样子。

**反悔条件**：如果哪天要做「窗口边框也玻璃化」，那必须走 DWM 路线，届时圆角改用
`DWMWA_WINDOW_CORNER_PREFERENCE`，Win10 用 `SetWindowRgn` 兜底。

## ADR-008 · 图标统一成方形圆角，但绝不加白底板

**决定**：先分析像素再决定怎么铺，圆角 = 边长 × 0.235。

**为什么不能只看「不透明占比」**
第一版用「不透明像素 > 70% 就当整块画」。正圆形的占比是 π/4 ≈ 78%，直接被误判，
裁完还是个圆，四个角漏出 Dock 底色——用户加的头像图标就是这么露馅的。

改用**边缘填充率**：沿四条边各取一条内缩 5% 的线，量这条线上不透明像素的比例。

| 图形 | 边缘填充率 |
| --- | --- |
| 整块方图 / 圆角方形 | ≈ 0.9 |
| 正圆 | ≈ 0.45 |

区分度足够大，阈值取 0.62。

**三档处理**

| 判定 | 处理 |
| --- | --- |
| 边缘填充率 ≥ 0.62 | 整块画 → 用 `ImageBrush` + 圆角矩形裁切，**零底板** |
| 边缘不连续，但量化主色占比 ≥ 28% | 主色即背景色 → 用它铺满圆角方形，图标按原尺寸叠上去，透明处自然露出同色，接缝不可见 |
| 其余（细字形） | 取对比色（亮字形配深底 / 暗字形配浅底，再降 25% 饱和）当底板，图标内嵌 14% |

**为什么不是「统一加一块白底板」**
第一版就是每个图标垫一块 `#F0FFFFFF` 的圆角底板。结果 Cursor 那种黑底图标外面多出一圈白框，
像贴了张标签纸。用户原话是「图标周围不要有白边」——白底板这条路直接废掉。

**代价**：极端情况下（图标主体是细线条、主色不集中）仍会落到对比色底板档，观感偏设计化。
要完全还原原图，只能给常见应用维护一张配色表，暂时不做。

## ADR-009 · 配置存 `%AppData%\AquaDesk\*.json`，不写注册表

**决定**：`settings.json` + `dock.json`，System.Text.Json，带缩进。

**理由**
- 注册表写进去容易、清出来难，卸载残留是流氓软件特征，跟「可逆」这条产品原则冲突。
- JSON 用户能直接看、能备份、能改，出问题删掉就恢复出厂。
- 所有 setter 都做区间收敛（`Clamp`），手改 JSON 写个负数也不会把界面搞崩。

**注意**：派生只读属性必须标 `[JsonIgnore]`，否则 `WindowHeight`、`TileRadius` 这些计算值会被一起序列化，
配置文件从 6 个字段膨胀成 20 多个，看着就脏。

## ADR-010 · 放大让位用「对称展开」，不追 macOS 的「光标锚定」

**决定**：玻璃条按 `自然宽度 + 总增量` 居中生长，图标位移按累加增量对称展开。

**理由**
- macOS 的做法是「光标下那个图标钉住不动，玻璃条左右不对称生长」。
- 我们的窗口宽度必须提前固定（每帧改窗口尺寸会抖），玻璃条只能在窗口内居中生长。
  如果硬要光标锚定，玻璃条会有一侧顶出窗口被裁掉。
- 对称展开的代价是：在 Dock 两端悬停时，光标下的图标会稍微往中间滑一点点。实测可接受。

**反悔条件**：如果以后把窗口做成全屏透明覆盖层（而不是贴底的小窗口），
窗口本身没有边界，就可以放心做光标锚定。

## ADR-011 · 折射靠抓屏 + 边缘形变，不靠 DWM 模糊

**决定**：每 70ms 抓一次 Dock 背后的屏幕区域，做可分离盒式模糊，然后在**靠近边缘 15px 的一圈**里
按法线方向把采样点往外推，写进 `WriteableBitmap` 当玻璃底层。

**为什么不是 Acrylic / Mica**
- DWM 的 backdrop 只能给「模糊」，给不了「弯折」。用户要的是玻璃边缘把后面的内容**扭曲**，
  这必须自己拿到像素做重采样。
- 而且 Acrylic 要求窗口不透明，和圆角方案冲突（见 ADR-005）。

**为什么只推边缘**
真玻璃中间是平的、边缘是弧的，光线只在边缘偏折。整块都推就成了放大镜。
推力用 `t²`（t = 距边缘的归一化距离），内圈几乎不动，到边界推到 1.15 倍边缘宽度。

**最关键的前提：必须把自己排除在捕获之外**
`SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`。不设的话，`BitBlt` 抓到的是 Dock 自己，
折射层把自己拍进去，下一帧又拍到「已经含自己」的画面，反复叠加会越来越亮——直接变成一坨白雾。

**自检机制**
启动时抓两次同一区域：一次带排除、一次临时取消排除。像素完全一致就说明排除没生效，
直接关掉折射层退回纯渐变。这样在老系统（Win10 2004 之前）上不会翻车。

**代价**
Dock 从此不会出现在任何截图/录屏里——捕获 API 会把它整个抹掉。这是这个方案绕不开的副作用。
另外 14fps 的刷新率意味着快速拖动窗口时，边缘有一点点延迟感。
